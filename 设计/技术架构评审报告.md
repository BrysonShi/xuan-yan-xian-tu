## 二、逐项评审

### 1. 记忆碎片匹配机制

#### 1.1 方案回顾

方案定义 `usableAtScenes: ['ch2_4', 'ch3_5', 'ch4_2']` 的白名单匹配方式。

#### 1.2 问题分析

**维护成本评估：🔴 高**

- 当前 storyGraph 已有 **35+ 个场景节点**，方案中记忆碎片需硬编码场景 ID 列表。
- 每新增一章（按当前速度 ~10 个场景/章），需要同步更新所有相关记忆碎片的 `usableAtScenes`。
- 更严重的问题：**场景 ID 的语义不稳定**。如果重构 storyGraph（如拆分场景、重命名），所有关联的记忆碎片都会失效。

**示例**：假设有碎片 `insight_liufei_pattern` 关联 `['ch2_4', 'ch3_5']`，后来 ch3_5 被拆分为 ch3_5a 和 ch3_5b，碎片就匹配不上了。

#### 1.3 严重程度：⭐ 重要

#### 1.4 改进建议

**替代方案：标签匹配（Tag-based Matching）**

```javascript
// 改为场景打标签 + 碎片匹配标签
{
  id: 'insight_liufei_pattern',
  name: '柳飞的暗器习惯',
  description: '先风刃远程，再近身绞杀',
  matchTags: ['npc:liufei', 'combat:暗器', 'conflict:对决'],
  // ...
}

// storyGraph 场景也带标签
'ch2_4': {
  text: '...',
  tags: ['npc:liufei', 'conflict:对决'],
  // ...
}
```

**优势**：
- 新增场景只需打标签，不需要逐个碎片更新
- 标签语义比场景 ID 稳定（"npc:liufei" 不会因为场景拆分而失效）
- 支持模糊匹配（`tags.includes` 或更灵活的权重匹配）

**退一步的方案**：如果不想改 storyGraph 结构，可以改为 **函数式匹配**：

```javascript
{
  matchFn: (sceneId, sceneData, playerState) => {
    // 任意逻辑判断
    return sceneId.startsWith('ch2') || sceneData.npc?.name === '柳飞';
  }
}
```

### 2. 每日次数重置机制

#### 2.1 方案回顾

```javascript
sim_daily: { date: '2026-08-18', count: 2 }
```

用日期字符串判断是否跨天。

#### 2.2 可靠性分析

**基本可靠性：🟡 中等**

- 日期字符串比较 `date === '2026-08-18'` 在单时区环境下是可靠的。
- **跨时区问题**：玩家在 UTC+8 的 23:50 启动一次模拟，模拟持续到 UTC+8 次日 00:10 结束。此时 `date` 还是 `'2026-08-18'`，但实际已是次日。这本身不是 bug（以启动时间为准是合理设计），但需要在文档中明确说明。

**真正的风险：跨时区切换**
- 玩家坐飞机从北京（UTC+8）到纽约（UTC-5），本地日期回退了 13 小时。
- 如果日期判断用的是 `new Date().toLocaleDateString()`（基于系统本地时间），玩家可以"倒流时间"获得额外模拟次数。
- 如果用的是 UTC 日期，则玩家可能在本地时间凌晨看到"次数没重置"。

#### 2.3 严重程度：🟡 建议（对单机游戏来说是低优先级）

#### 2.4 改进建议

```javascript
// 方案 A（推荐）：使用 UTC 日期，并在文档中声明"每日"以 UTC 为准
function getUTCDateStr() {
  return new Date().toISOString().slice(0, 10); // '2026-08-18'
}

// 方案 B：记录重置时间戳，用绝对时间差判断
sim_daily: {
  lastResetTimestamp: 1724000000000,
  count: 2,
}
// 重置逻辑：if (now - lastResetTimestamp > 24 * 3600 * 1000) { reset }
```

**实际建议**：这是个单机游戏，跨时区作弊不是核心关注点。用方案 A（UTC 日期）即可，简单可靠。在代码注释中注明设计意图。

### 3. 天机反噬概率公式

#### 3.1 方案回顾

```javascript
function getDeathProbability(yearsElapsed, realmLevel) {
  const baseChance = 0.02;
  const realmFactor = 1 + realmLevel * 0.1;
  const timeFactor = 1 + (yearsElapsed / 20);
  return Math.min(0.3, baseChance * realmFactor * timeFactor);
}
```

#### 3.2 数值模拟分析

我模拟了不同境界、不同年份下的死亡概率曲线：

| 年份 | 炼气一层(L0) | 炼气五层(L4) | 炼气九层(L8) |
|------|-------------|-------------|-------------|
| 1 | 2.0% | 2.8% | 3.6% |
| 5 | 2.5% | 3.5% | 4.5% |
| 10 | 3.0% | 4.2% | 5.4% |
| 20 | 4.0% | 5.6% | 7.2% |
| 40 | 6.0% | 8.4% | 10.8% |
| 60 | 8.0% | 11.2% | 14.4% |
| 80 | 10.0% | 14.0% | 18.0% |

**累计存活率（估算）**：假设每年独立判定一次死亡概率，则存活 N 年的概率 = ∏(1 - p_i)。

- 炼气一层：80 年累计死亡率 ≈ 65%（存活率 35%）—— 合理
- 炼气九层：80 年累计死亡率 ≈ 91%（存活率 9%）—— 偏高，高境界玩家基本活不到 80 年
- 炼气九层 40 年累计死亡率 ≈ 55% —— 这意味着高境界模拟平均只能活 ~35 年

#### 3.3 核心问题

**问题 1：高境界活得反而更短（反直觉）**

`realmFactor = 1 + realmLevel * 0.1` 让高境界的死亡概率 **更高**，这与修仙世界观矛盾——境界越高应该活得越久。

方案中注释写的是"高境界活得久一点"，但公式实际效果相反。这可能是设计意图（高境界推演的"天机"更强大所以反噬更厉害？），但与直觉不符，需要在文档中解释。

**问题 2：公式可能让模拟太短**

如果每年还有战斗场景的额外死亡概率（方案中提到"战斗/冒险场景有概率死亡"），叠加天机反噬后，高境界模拟可能在 15-20 年就结束。对于一次消耗 200 灵石的模拟来说，体验太差。

**问题 3：没有保底机制**

没有"至少活 N 年"的保底。极端情况下，第一年就死了（2% 概率虽然低，但在大量模拟中会出现）。

#### 3.4 严重程度：⭐⭐ 重要

#### 3.5 改进建议

```javascript
// 修正方案：
// 1. 反转境界因子——高境界更耐活
// 2. 加入保底年限
// 3. 前 N 年免疫天机反噬
function getDeathProbability(yearsElapsed, realmLevel) {
  // 保底：前 5 年不会因天机反噬死亡
  if (yearsElapsed < 5) return 0;
  
  const baseChance = 0.01; // 降低基础概率
  // 高境界活得久：realmLevel 越高，概率增长越慢
  const realmResist = 1 - realmLevel * 0.05; // 炼气九层减免 40%
  const timeFactor = Math.pow(yearsElapsed / 30, 1.5); // 超线性增长，30年后急剧增加
  
  const p = baseChance * realmResist * timeFactor;
  return Math.min(0.15, p); // 上限从 0.3 降到 0.15
}
```

这样炼气九层 80 年累计死亡率约 45%，炼气一层约 80%，更符合直觉。

### 4. 存档兼容性

#### 4.1 问题分析

设计文档提到新增字段：
- `player.memoryFragments` / `player.simInsights`
- `player.flags.sim_daily`

查看当前代码：

| 字段 | player.js 默认值 | simStore.js 使用 | 兼容性 |
|------|-----------------|-----------------|--------|
| `memoryFragments` | ✅ 已有 `[]` | 方案中提到但未实现 | 🟡 存在命名混乱 |
| `simInsights` | ✅ 已有 `[]` | ✅ restoreAndMerge 中使用 | ✅ 兼容 |
| `flags.sim_daily` | ❌ 未定义 | 方案中提到但未实现 | 🔴 旧存档缺失 |
| `stats.totalSimulations` | ✅ 已有 | ✅ 已使用 | ✅ 兼容 |
| `stats.longestLife` | ✅ 已有 | ✅ 已使用 | ✅ 兼容 |

#### 4.2 核心风险

**风险 1：命名混乱**

player.js 中同时存在 `memoryFragments: []` 和 `simInsights: []`，设计文档中也交替使用"记忆碎片"和"insight"。需要明确：
- `memoryFragments` 和 `simInsights` 有什么区别？
- 设计文档中的 `memoryFragments` 到底对应哪个字段？

**风险 2：旧存档缺少 `sim_daily`**

已有存档中不会有 `flags.sim_daily`，代码读取时必须做防御性处理。

**风险 3：version 字段未使用**

player.js 有 `version: '0.1.0'`，但没有存档迁移机制。

#### 4.3 严重程度：🔴 重要（可能导致老存档数据丢失或报错）

#### 4.4 改进建议

```javascript
// 1. 统一命名：只保留一个字段
// 建议保留 memoryFragments，废弃 simInsights
// 或在 player.js 中明确注释二者的区别

// 2. 增加存档迁移函数
function migrateSaveData(data) {
  const version = data.version || '0.0.0';
  
  // 0.1.0 → 0.2.0：新增 sim_daily
  if (!data.flags.sim_daily) {
    data.flags.sim_daily = { date: '', count: 0 };
  }
  
  // 迁移 simInsights → memoryFragments
  if (data.simInsights?.length && !data.memoryFragments?.length) {
    data.memoryFragments = data.simInsights.map(id => ({
      id,
      acquiredAt: Date.now(),
      used: false,
    }));
  }
  
  data.version = '0.2.0';
  return data;
}

// 3. 所有新增字段的读取都使用可选链
// ❌ player.sim_daily.count
// ✅ player.sim_daily?.count ?? 0
```

### 5. 模拟中的随机事件

#### 5.1 方案回顾

方案提出"从预定义池还是动态生成"的待讨论问题。

#### 5.2 技术分析

**预定义事件池（推荐 ✅）**

```javascript
// 预定义：可控、可测试、质量有保障
const SIM_RANDOM_EVENTS = [
  {
    id: 'sim_spring_pool',
    text: '山间灵泉突然涌出大量灵气，你趁机修炼。',
    condition: (state) => state.realmLevel <= 3,
    weight: 10,
    effect: { cultivation: 300 },
  },
  {
    id: 'sim_robbery',
    text: '一名蒙面散修拦住去路，要你留下灵石。',
    condition: (state) => state.resources.spiritStones > 20,
    weight: 5,
    // ...
  },
];
```

**优势**：
- 文本质量可控（修仙文风需要人工把控）
- 可以精确控制概率和平衡
- 易于测试和调试
- 与现有 storyGraph 的模式一致

**劣势**：
- 需要维护事件池，每次新增内容需要手写
- 事件数量受限于人工投入

**动态生成（不推荐 ❌）**

```javascript
// 动态生成：需要模板系统或 LLM
function generateRandomEvent(playerState) {
  const templates = [
    '你在{地点}遇到了{event}，{outcome}。',
    // ...
  ];
  // 填充模板...
}
```

**问题**：
- 纯模板拼接的文本质量很差，与 storyGraph 精心撰写的文案差距明显
- 如果用 LLM 生成，引入外部依赖、延迟、成本问题
- 难以保证叙事连贯性和平衡性

#### 5.3 严重程度：🟡 建议（设计阶段决策）

#### 5.4 改进建议

**采用"预定义池 + 标签路由"方案**：

```javascript
const SIM_RANDOM_EVENTS = [
  {
    id: 'sim_encounter_liufei',
    tags: ['npc:liufei'],
    text: '在坊市中偶遇柳飞，他似乎没注意到你……',
    condition: (state, startScene) => {
      // 只有在起始场景与柳飞相关时才出现
      return startScene.tags?.includes('npc:liufei');
    },
    // ...
  },
];

// 事件选择器
function pickRandomEvent(playerState, startScene) {
  const candidates = SIM_RANDOM_EVENTS.filter(
    e => !e.condition || e.condition(playerState, startScene)
  );
  // 加权随机
  const totalWeight = candidates.reduce((s, e) => s + (e.weight || 1), 0);
  let roll = Math.random() * totalWeight;
  for (const e of candidates) {
    roll -= (e.weight || 1);
    if (roll <= 0) return e;
  }
  return candidates[0];
}
```

### 6. 模拟文本风格改造

#### 6.1 现状分析

当前 storyGraph 的 `text` 字段支持两种形式：
- **字符串**：大部分场景
- **函数**：如 `ch2_1` 中 `text: (realm, stones) => \`...\``

SimulationView 中已有对应处理：
```javascript
if (typeof scene.text === 'function') {
  sceneText = scene.text(realm, stones);
} else {
  sceneText = scene.text;
}
```

**问题**：同一个 storyGraph 被 RealityView 和 SimulationView 共用，但两种模式需要不同的文本风格（沉浸式 vs 命运投影）。

#### 6.2 严重程度：⭐ 重要（影响核心体验）

#### 6.3 改造方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 双 text 字段 | 每个场景加 `simText` 字段 | 清晰分离 | 35+ 场景 × 2 份文本，维护成本翻倍 |
| B. 文本包装器 | 在 SimulationView 中用 wrapper 包裹原文本 | 改动最小 | 无法做到真正的风格差异 |
| C. 风格适配器 | 新增 `simTextTransform` 函数统一转换 | 复用原文本 | 简单正则/替换很难做好风格转换 |
| **D. 混合方案（推荐）** | 核心场景写 `simText`，其余用 wrapper | 平衡工作量和质量 | 需要定义哪些是"核心场景" |

#### 6.4 推荐实现

```javascript
// storyGraph 场景扩展
'mountain_1': {
  text: '原文本（现实模式用）...',
  simText: '你看到自己走进了后山的密林，模糊的画面一闪而过……', // 模拟模式专用
  simTextFn: (state) => `命运投影中，你${state.realm}的修为在山间若隐若现……`, // 或动态函数
  // ...
}

// SimulationView 中优先读取 simText
function getSceneText(scene, simState) {
  if (scene.simTextFn) return scene.simTextFn(simState);
  if (scene.simText) return scene.simText;
  // fallback：用 wrapper 包装原文本
  return `命运投影闪烁——\n「${typeof scene.text === 'function' ? scene.text(simState.realm, simState.stones) : scene.text}」`;
}
```

**分阶段实施**：
1. **Phase 1**：先用 fallback wrapper，所有场景统一加「命运投影闪烁——」前缀
2. **Phase 2**：为核心场景（柳飞对决、洞府探索等）手写 `simText`
3. **Phase 3**：逐步覆盖更多场景

## 三、额外发现的技术风险

### 风险 E1：SimulationView 的场景遍历逻辑过于简单 🔴 重要

当前 `SimulationView.vue` 中的静修推进逻辑（`advanceIdle`）：

```javascript
// 40%概率触发场景事件
if (Math.random() < 0.4 && simStore.saveSnapshot) {
  const startScene = simStore.saveSnapshot.sceneId;
  const startSceneData = storyGraph[startScene];
  // 从起始场景的几个选项分支中随机选一个
  const randChoice = startSceneData.choices[Math.floor(Math.random() * startSceneData.choices.length)];
  if (randChoice.next) loadScene(randChoice.next);
}
```

**问题**：
- 只从起始场景的直接子节点中选，很快就会重复
- 没有"深入遍历"能力——永远只能看到起始场景的邻居
- 当 storyGraph 扩展后，这种浅层随机会让模拟体验极度单调

**建议**：实现一个图遍历引擎，支持随机深度遍历：
```javascript
function getRandomReachableScene(startSceneId, maxDepth = 3) {
  let current = [startSceneId];
  for (let d = 0; d < maxDepth; d++) {
    const nextSet = new Set();
    for (const id of current) {
      const scene = storyGraph[id];
      if (scene?.choices) {
        scene.choices.forEach(c => c.next && nextSet.add(c.next));
      }
    }
    if (nextSet.size === 0) break;
    current = [...nextSet];
  }
  return current[Math.floor(Math.random() * current.length)];
}
```

### 风险 E2：simStore 的 applySimEffect 与 player model 耦合 ⭐ 建议

`applySimEffect` 直接操作 `simPlayerState` 的原始属性（`p.cultivation`、`p.resources.spiritStones`），与 `player.js` 的 `REALM_TABLE` 硬耦合。如果后续修改境界系统，需要同步修改 simStore。

**建议**：将突破逻辑抽到 `CalculationEngine` 或 `player.js` 的共享函数中。

### 风险 E3：结算页奖励生成缺少种子随机 ⭐ 建议

`SettlementView.vue` 中的 `generateRewards()` 使用 `Math.random()`，每次进入结算页都会重新生成（如果玩家刷新页面）。虽然 `onMounted` 只执行一次，但如果有路由缓存问题可能导致奖励变化。

**建议**：奖励池在 `simStore.endSimulation()` 时生成并锁定，而不是在 SettlementView 的 `onMounted` 中。

### 风险 E4：设计文档与代码的消耗单位不一致 🟡

设计文档说消耗"灵石"（ spiritStones），但 `SimulationView.vue` 中显示的是"天机点"（destinyPoints）：
```html
<span class="sim-header__cost text-dim font-num">天机点 {{ destinyCost }}</span>
```

`player.js` 中 `DEFAULT_RESOURCES` 没有 `destinyPoints`，但 `applySimEffect` 中有处理。需要统一消耗资源类型。

| R10 | 结算奖励在 View 层生成而非 Store | **建议** | 系统一致性 | 移入 simStore |
| R11 | 随机事件生成方式未决策 | **建议** | 技术可行性 | 采用预定义池+标签路由 |
| R12 | applySimEffect 与 player model 耦合 | **建议** | 技术可行性 | 抽取共享逻辑 |

**严重程度分布**：
- 🔴 致命：0 个
- ⭐ 重要：7 个（R1-R7）
- 🟡 建议：5 个（R8-R12）

## 五、总体结论

设计方案的核心创意——"信息差优势"驱动的命运模拟器——在技术上是完全可行的，与现有代码架构的整合方向也正确。

**主要改进优先级**：
1. 🥇 **统一命名并增加存档迁移**（R3 + R4）—— 这是上线前必须解决的
2. 🥈 **修正天机反噬公式**（R2 + R7）—— 直接影响核心玩法体验
3. 🥉 **改造记忆碎片匹配为标签机制**（R1）—— 影响后续内容扩展效率
4. 🏅 **实现图遍历引擎**（R5）—— 决定模拟内容的丰富度

方案中没有发现致命级风险，但上述重要级问题建议在开发前解决，可以避免大量返工。
